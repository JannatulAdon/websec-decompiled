File Upload Vulnerabilities · The Core Investigation ​

An upload form is an open invitation for visitors to write raw bytes directly onto the server's hard drive. The vulnerability happens when the server decides what a file is based on labels the user controls, stores it inside an executable folder, and then asks an execution engine to run it.

💡 Everyday Analogy: The Trophy with a Secret Engine. Imagine a community center that allows visitors to donate trophies for display in the glass foyer. If a visitor brings in a wooden trophy labeled "Harmless Statue", but secretly hollows out the base and installs an active remote-control engine, placing it in the foyer gives the visitor control over the room. Real security means checking the physical material (not just the shipping label), stripping active mechanisms, and placing it in a separate, non-conductive storage room.

Case File #1: Following an Uploaded File Behind the Curtain ​

Let's trace what happens when you update your profile avatar on a web application.

🔎 Step 1 · What You Notice in the Browser

You click "Change Avatar", select an image on your computer, and press "Upload". Your browser packages the image into a multipart/form-data HTTP request with a filename="avatar.png" attribute and a Content-Type: image/png header, then posts it to /my-account/avatar.

⚙️ Step 2 · What the Server Does Behind the Scenes

The server receives the byte stream, extracts the filename and header, checks if the extension is acceptable, and writes the bytes into a publicly accessible folder like /var/www/html/avatars/avatar.png so that the browser can display it later.

Blue = Server Storage PathGold = Client-Provided Filename
/var/www/html/avatars/avatar.png
💥 Step 3 · Where the Logic Breaks

The client completely controls the filename and the Content-Type header. If a user uploads a server-side script (such as a PHP or ASP file), and the server stores it inside the web root where script execution is enabled, visiting the file's URL causes the web server's runtime interpreter to execute the file instead of merely serving it as static image bytes.

🛡️ Step 4 · How Developers Lock It Down

Developers isolate uploads outside the public web root, generate random alphanumeric filenames (e.g., UUIDs) rather than trusting client filenames, re-encode uploaded images through an image processing library, and disable script execution permissions on storage folders.

Visual Comparison: Trusted Label vs. Actual Bytes ​

💭 What the Developer Expected

The developer believed checking Content-Type: image/png in the incoming HTTP header guaranteed that only legitimate graphic image files would be saved into the avatar directory.

💥 What Actually Happened

HTTP headers are authored entirely by the client. An intercepting proxy allowed sending a script file named shell.php while keeping Content-Type: image/png, tricking the server into saving executable code into a web-served folder.

🔬 Under the Hood: Why Web Servers Handle Filenames Differently

Filename parsing differences between web servers and operating systems often create unexpected execution paths:

  • Apache mod_mime and MultiViews: Apache can evaluate extensions from right to left or across multiple dots. If configured with handler mapping, a file named exploit.php.jpg may be executed as PHP if the server maps .php to the PHP handler regardless of trailing extensions.
  • IIS Semicolon Parsing: Historically, older IIS servers truncated filenames at semicolons (exploit.asp;.jpg), passing exploit.asp to the ASP handler while the validator only verified the trailing .jpg.
  • Nginx cgi.fix_pathinfo=1: If Nginx is paired with PHP-FPM with cgi.fix_pathinfo enabled, requesting /uploads/photo.jpg/test.php causes PHP to look for test.php, fail, and walk back up the path to execute photo.jpg as PHP.
⚙️ Engine Variations: Executable Extensions by Stack

Different application runtimes look for different file extensions:

  • PHP: .php, .php3, .php4, .php5, .phtml, .phar (which can trigger object deserialization on file operations).
  • ASP.NET: .aspx, .ashx, .asmx, .config (uploading a custom web.config can enable script execution in that folder).
  • Java: .jsp, .jspx, .war (if the application server auto-deploys WAR archives).
  • Node.js: Node does not execute files based on extensions by default; risks arise when uploaded templates or JavaScript modules are dynamically imported or rendered by a template engine.
  • Python: .py files do not execute automatically unless dynamically imported or evaluated by the app.

2. Path Traversal & Filename Manipulation ​

If the server takes the client-supplied filename and concatenates it directly into the save path without sanitization, path traversal sequences (../ or ..%2f) can write the file into a parent folder that does execute scripts.

💡 Detective Tip: Bypassing Blocklists with Configuration Files

If an application blocks .php extensions, developers may still have forgotten to block server configuration files. On Apache servers, uploading a custom .htaccess file can map an otherwise harmless extension (like .l33t or .png) to the PHP handler:

apache
AddType application/x-httpd-php .l33t
1

Once that .htaccess is uploaded into the folder, uploading exploit.l33t will execute as live PHP!

4. Non-Atomic Uploads & Race Conditions ​

Many applications save an uploaded file into a temporary directory first, run validation or an antivirus scan, and delete the file if it fails. If an investigator fires hundreds of GET requests for temp-9823.php while the upload is being processed, requests that hit during that 20ms window between Step 1 and Step 3 will successfully execute before the cleanup finishes.

The Detective's Upload Testing Checklist ​

When investigating an upload form, proceed systematically:

  1. Test Baseline Upload: Upload a legitimate image (avatar.png) and observe the response: Where is it saved? What URL does the page use to display it?
  2. Inspect Content-Type Trust: Upload a script file while modifying Content-Type to image/png. Does the server accept it?
  3. Test Extension Variations: If .php is blocked, test .phtml, .php5, .phar, or configuration files like .htaccess.
  4. Test Path Traversal: Supply filename="../avatar.png" or filename="..%2favatar.png" to see if the file lands in a parent directory.
  5. Test Magic Bytes & Polyglots: Prepend valid file signatures (like GIF89a;) or embed payloads into image EXIF/comment sections.
  6. Test Concurrency: If validation deletes files after saving, test for race conditions using parallel requests.

How Developers Lock It Down Permanently ​

Secure file handling requires defense in depth across all four lifecycle stages:

🛡️ The Golden Rules of Secure Uploads:

  • Store Outside Web Root: Store uploaded files in an isolated private directory or cloud storage bucket (e.g., AWS S3, Google Cloud Storage) completely separated from executable code.
  • Generate Random Names: Never use client-supplied filenames on disk. Assign a generated UUID and append an extension determined by the server's own strict allow-list.
  • Re-Encode Media: Process images through an image processing library (e.g., ImageMagick or Sharp) to strip comments and regenerate pixel data from scratch, neutralizing polyglots.
  • Disable Execution: Configure the web server to disable execution engines (e.g., php_flag engine off or Nginx location ^~ /uploads/ { } with no script handler).
  • Safe Download Headers: Serve user-uploaded downloads with Content-Disposition: attachment and X-Content-Type-Options: nosniff to prevent browser mime-sniffing execution.
