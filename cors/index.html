Cross-Origin Resource Sharing (CORS) · The Case of the Open Door ​

CORS (Cross-Origin Resource Sharing) is not a vulnerability in itself—it is a controlled door in the browser's Same-Origin Policy. By default, web browsers strictly forbid scripts on one website from reading private data fetched from another website. CORS allows a server to relax this restriction. The vulnerability arises when a server gives that read permission away to everyone, trusts invalid origins, or echoes back whatever domain happens to ask.

💡 Everyday Analogy: The Overly Polite Receptionist. Imagine a company office where confidential customer files are kept behind a front desk. Company rules state that only badged staff may read the files. A visitor arrives wearing a badge from a rival firm and asks: "May I have copies of your customer records?" Instead of verifying the visitor against an approved contractor list, the polite receptionist simply repeats the guest's badge name: "Welcome, rival-firm.com! Here is full access to the filing cabinet."

Case File #1: Tracing the Reflected Origin Trap ​

Let's follow what happens when an attacker tries to read your account details using a cross-origin script.

🔎 Step 1 · What You Notice in the Browser

You are logged into your shopping account on store.example. In another tab, you browse a totally unrelated entertainment blog on evil.example. The blog looks normal and no alerts appear.

⚙️ Step 2 · What the Server Does Behind the Scenes

JavaScript running on evil.example issues a cross-origin fetch() request to https://store.example/accountDetails. The browser adds an Origin: https://evil.example header. The store's backend blindly copies that origin into its response headers:

Blue = Server CORS ConfigurationGold = Reflected Origin Header
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://evil.example
Access-Control-Allow-Credentials: true
💥 Step 3 · Where the Logic Breaks

The browser inspects the response headers. Because the server explicitly granted permission to evil.example and allowed credentials (Access-Control-Allow-Credentials: true), the browser releases the response body to the attacker's script—exposing the victim's email, private address, and API keys!

🛡️ Step 4 · How Developers Lock It Down

Developers configure strict server-side allow-lists containing only explicitly trusted domain names. If the request's Origin header does not match the allow-list, the server does not send the Access-Control-Allow-Origin header, keeping the data safely protected by the Same-Origin Policy.

Visual Comparison: Intended API Sharing vs. Universal Origin Reflection ​

💭 What the Developer Expected

The developer wanted their frontend mobile site or trusted partner domain to read API data seamlessly without getting blocked by browser cross-origin security rules.

💥 What Actually Happened

By echoing whatever Origin header arrived in the request, the server inadvertently allowed every malicious site on the internet to read authenticated, confidential responses.

The Cross-Origin Request Lifecycle ​

How the browser handles a cross-origin request depends on whether it is classified as a simple request or requires a preflight check:

1. Script Issues Fetch External page initiates cross-origin request with credentials: 'include'.
→
2. Browser Stamped Origin Browser automatically adds authentic Origin: https://evil.example header.
→
3. Preflight OPTIONS (if complex) Checks allowed methods, headers, and credentials before sending real request.
→
4. Server Response Headers Server answers with ACAO and ACAC access directives.
→
5. Browser Enforcement Browser permits script to read response body or blocks access.
🔬 Under the Hood: Why Credentials Change the Rules
  • Wildcard Origins: A server can send Access-Control-Allow-Origin: * for public data. However, the browser strictly rejects the wildcard if Access-Control-Allow-Credentials: true is set.
  • Credentialed Requests: To read authenticated responses (which include cookies or HTTP authentication), the server must return an explicit, concrete origin in Access-Control-Allow-Origin.
  • Cache Poisoning Prevention: If a server dynamically reflects the origin, it must include the Vary: Origin header. Otherwise, a shared caching proxy might store a response authorized for an attacker and serve it to legitimate users!

Origin Reflection: The Universal Pass ​

The most common CORS vulnerability occurs when developers want to support multiple internal subdomains, and solve it by simply copying the incoming Origin header directly into Access-Control-Allow-Origin.

An attacker's page on any domain can send a credentialed request, receive full read authorization from the browser, and exfiltrate the victim's sensitive data.

The Trusted null Origin Trap ​

When developers want to test cross-origin requests locally or allow sandboxed content, they sometimes add null to their CORS allow-list (Access-Control-Allow-Origin: null).

The Origin: null header is generated in several browser situations:

  • HTML documents loaded inside an <iframe sandbox>
  • Local file:// resources
  • Cross-origin redirects under certain privacy configurations

An attacker can host an exploit inside a sandboxed iframe. The browser automatically assigns Origin: null to the outgoing request, satisfying the server's allow-list and stealing the response!

💡 Detective Distinction: CORS vs. CSRF

It is common for beginners to confuse CORS and CSRF:

  • CSRF is about WRITING (Actions): An attacker tricks your browser into performing an action (like changing an email or posting a message). The attacker does not need to read the server's answer.
  • CORS is about READING (Data Theft): An attacker wants to read private data (like account balances, personal messages, or API keys). The Same-Origin Policy stops the read; flawed CORS headers unlock it.

🛡️ The Detective's Defense Blueprint. Never dynamically reflect incoming Origin headers into Access-Control-Allow-Origin. Maintain a strict, hardcoded allow-list of exact HTTPS origins. Never allow the null origin. Always send the Vary: Origin header whenever responses vary by origin. Remember that CORS is an access control mechanism for browsers, not authentication.
