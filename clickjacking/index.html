Clickjacking · The Case of the Invisible Trapdoor ​

Clickjacking (also known as a UI Redressing attack) does not break network encryption or exploit memory bugs. Instead, it tricks the human in front of the screen. An attacker loads a target website inside an invisible frame, places an enticing decoy button directly in front of it, and hijacks the user's authentic mouse click to trigger sensitive account actions.

💡 Everyday Analogy: The Stencil Over the Contract. Imagine a salesperson hands you a fun crossword puzzle with a small cutout window where you are asked to write a checkmark to win a free coffee. Unknown to you, placed directly underneath the cardboard stencil is an official contract to transfer the title of your car—and your checkmark lands right on the signature line. You intended to claim a coffee, but your physical pen stroke signed away your property.

Case File #1: Tracing the Transparent Iframe Heist ​

Let's see how an attacker turns a routine account settings page into an invisible trap.

🔎 Step 1 · What You Notice in the Browser

You visit a promotional page offering a free prize. In the center of the page is a large, colorful button that says: "Click Here to Claim Free Gift!" Everything looks harmless and playful.

⚙️ Step 2 · What the Attacker Page Does Behind the Scenes

Layered directly on top of the decoy button is an <iframe> loading the user's real account page on https://target-bank.example/account/delete. The iframe has opacity: 0.0001 (virtually invisible) and a higher z-index:

Blue = Decoy UI Visible to VictimGold = Invisible Iframe Layered on Top
<button style="position: absolute; top: 300px; left: 100px; z-index: 1;">Claim Free Gift</button>
<iframe src="https://target-bank.example/account/delete" style="opacity: 0.0001; position: absolute; top: 280px; left: 90px; z-index: 2;"></iframe>
💥 Step 3 · Where the Logic Breaks

Because the victim is logged into target-bank.example, the browser renders their authenticated account page inside the frame. When the user clicks the decoy button, the mouse click is intercepted by the invisible top layer—landing directly on the bank's "Confirm Account Deletion" button!

🛡️ Step 4 · How Developers Lock It Down

Developers send HTTP response headers that forbid third-party websites from framing sensitive pages. By setting Content-Security-Policy: frame-ancestors 'none' (or legacy X-Frame-Options: DENY), the browser refuses to render the page inside any iframe.

Visual Comparison: Decoy Surface vs. Invisible Trapdoor ​

💭 What the Developer Expected

The developer assumed that because the account deletion page is protected by CSRF tokens and requires an explicit button click, an attacker could never automate the action from another website.

💥 What Actually Happened

The attacker never had to forge a request or steal a token. They simply framed the real page, made it invisible, and tricked the victim into performing the genuine physical click themselves.

The UI Redress Layering Mechanism ​

A clickjacking attack works by aligning layers in the browser's visual viewport:

1. Decoy Webpage Attacker displays tempting decoy UI (game, quiz, or prize button).
→
2. Authenticated Iframe Target website loaded invisibly via opacity: 0.0001.
→
3. Coordinate Alignment Target action button positioned precisely beneath the decoy cursor.
→
4. Unwitting Click Victim clicks decoy; hit-test event lands on the transparent iframe.
→
5. Action Executed Target application processes legitimate authenticated click.
🔬 Under the Hood: Why Opacity is Used Instead of display:none

If an attacker styles an iframe with display: none or visibility: hidden, the browser does not render the element in the layout tree and it cannot receive mouse events.

By setting opacity: 0.0001, the iframe remains fully rendered and active in the browser's hit-testing pipeline. The minuscule opacity value avoids browser rendering optimizations that might skip painting completely transparent elements.

Prefilled Form Inputs & CSRF Protections ​

Some web applications accept parameters from the URL to prefill forms (e.g. ?email=attacker@malicious.com). When clickjacking is combined with URL prefilling, the attacker only needs to entice the user into a single click to submit the pre-populated form!

Even if the target form contains robust anti-CSRF tokens, the attack succeeds because the submission is generated natively inside the genuine, framed document.

The Failure of JavaScript Frame Busters ​

Before standard HTTP security headers existed, developers attempted to block framing using client-side JavaScript "frame buster" scripts:

js
// Naive frame-buster script
if (top !== self) {
  top.location = self.location;
}
1
2
3
4

These scripts are easily defeated:

  • HTML5 Sandboxing: An attacker can frame the page with <iframe sandbox="allow-forms allow-scripts"> while omitting allow-top-navigation, preventing the frame buster from redirecting the top-level window.
  • Navigation Interception: The attacking parent window can listen to onbeforeunload and prompt the user to cancel any attempted redirection.

Chaining Clickjacking with DOM XSS ​

If a target page has a DOM-based XSS flaw that requires user interaction (such as an anchor tag with a javascript: URL or a button with an onclick handler), an attacker can supply the payload in the iframe's URL and use clickjacking to supply the necessary user activation.

The victim clicks what they think is a harmless game button, triggering the client-side sink and executing the script.

Multi-Step Confirmation Flows ​

Many sensitive actions involve two steps: a first click to initiate the action and a second click in a confirmation modal. Clickjackers overcome this by creating multi-stage decoy games (like "Whack-a-Mole" or "Click twice to verify your age"), moving the decoy button between clicks to match the shifting coordinates of the modal dialog.

⚙️ Defensive Headers: X-Frame-Options vs. CSP frame-ancestors
  • X-Frame-Options: DENY: Blocks all framing attempts on any origin.
  • X-Frame-Options: SAMEORIGIN: Permits framing only by pages on the exact same origin.
  • Content-Security-Policy: frame-ancestors 'none': The modern standard. Replaces X-Frame-Options and allows specifying exact allowed ancestor domains (frame-ancestors 'self' https://trusted-partner.com).

When both headers are present, modern browsers give precedence to CSP frame-ancestors.

🛡️ The Detective's Defense Blueprint. Always send Content-Security-Policy: frame-ancestors 'none' (or an explicit allow-list) on all authenticated pages. For legacy browser support, include X-Frame-Options: DENY. Never rely on client-side JavaScript frame-busting scripts. For highly sensitive operations like password changes or fund transfers, require re-authentication or multi-factor confirmation.
