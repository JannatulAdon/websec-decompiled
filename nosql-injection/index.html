NoSQL Injection · The Document Query Investigation ​

Many developers assume that switching from SQL to NoSQL automatically cures injection bugs. In reality, NoSQL databases don't eliminate injection—they just change the grammar. Instead of injecting SQL keywords through broken single quotes, an attacker passes structured JSON objects carrying special database operators that rewrite the query rules from the inside out.

💡 Everyday Analogy: The ID Card vs. The Rulebook. Imagine walking into an exclusive club where a security guard checks names at the door. Normally, you hand the guard an ID card with your name printed as text: "Alice". If the name is on the guest list, the guard unlocks the door. But suppose instead of an ID card with text, you hand the guard an official laminated rule card from the club manager that says: "Admit any visitor whose name is NOT empty." If the guard blindly treats the rule card as your ID, the guest list check is bypassed instantly. In NoSQL injection, query operators like $ne act like that laminated rule card.

Case File #14: Following a Document Query Behind the Scenes ​

Let's trace what happens when you attempt to log in to an application powered by Node.js, Express, and MongoDB.

🔎 Step 1 · What You Notice in the Browser

You fill out a login form with a username and password. When you click Log In, your browser packages your credentials into a JSON payload and sends a POST /login request:

{"username": "admin", "password": "password123"}
⚙️ Step 2 · What the Server Does Behind the Scenes

The Express backend uses a JSON body parser to convert that payload directly into a JavaScript object. It then passes those fields straight into a MongoDB collection search query without validating what type of data arrived:

Blue = Backend Query FilterGold = Values From Your Request
db.users.findOne({ "username": "admin", "password": "password123" })
💥 Step 3 · Where the Logic Breaks

Because the application trusts the JSON structure sent by the client, an attacker doesn't send a plain text string for the password. Instead, they send a nested JSON object containing a NoSQL query operator📖 NoSQL Query Operator ($ne, $regex)Special JSON keys starting with `$` in databases like MongoDB that mean "not equal to" or "matches pattern" instead of plain text.💡 Real-life analogy: Instead of handing a guard a password, handing them an official rulebook card that says "Accept anything that is NOT blank.": {"$ne": ""}. MongoDB interprets keys starting with $ as query commands rather than literal passwords. The query now matches any user whose password is not equal to an empty string, immediately returning the administrator account!

🛡️ Step 4 · How Developers Lock It Down

Developers enforce strict data types. Before passing input into any database call, they verify that typeof req.body.password === 'string' or use schema validation libraries like Zod or Mongoose schemas. If an attacker submits an object instead of a string, the validator rejects the request before it ever reaches the database.

Visual Comparison: Plain Text vs. Query Operator ​

💭 What the Developer Expected

The developer assumed req.body.password would always be a string like "MyP@ssw0rd!". MongoDB would perform an exact literal string comparison against the stored user credential.

💥 What Actually Happened

The client submitted an object {"$ne": null}. MongoDB's query engine parsed $ne as the built-in "Not-Equal" operator. Since every existing account has a password that isn't null, the condition evaluated to true for the first user found.

Watch the Query Transform Color by Color ​

Observe how changing the data type of the input transforms a simple search parameter into an active logical condition:

Blue = Application Query SkeletonGold = Injected Operator Object
db.users.findOne({ "username": "admin", "password": { "$ne": "" } })
🔬 Under the Hood: String vs. Object Types in MongoDB

Unlike SQL, where queries are represented as plain text strings that get parsed and tokenized, MongoDB queries are structured documents (BSON/JSON objects).

When a Node.js server does:

javascript
db.collection('users').findOne({
  username: req.body.username,
  password: req.body.password
});

Furthermore, Express's body-parser with extended: true parses URL-encoded form data into nested objects! Sending password[$ne]= in a standard HTML form produces { password: { "$ne": "" } } on the server even when the API doesn't accept JSON.

Essential NoSQL Operators: The Detective's Cheat Sheet ​

When probing a NoSQL endpoint, you aren't looking for syntax errors caused by broken quotes. Instead, you're observing whether the server treats operator objects as live instructions:

OperatorPlain-English MeaningInvestigation Role
$ne"Not equal to"Bypasses exact-value checks by asserting the field is not null or not empty.
$gt / $gte"Greater than" / "Greater than or equal"Can be tested against empty strings ({"$gt": ""}) to match any string.
$in / $nin"Value matches any in list"Tests multiple possibilities at once without running multiple queries.
$regex"Matches regular expression pattern"Allows blind character-by-character brute forcing like a combination lock.
$where"Execute arbitrary JavaScript code"Evaluates server-side JavaScript expressions per document.

Phase 1: Probing for Operator Injection & Auth Bypass ​

When auditing a login endpoint or API search filter, the first goal is to determine if the backend accepts structured objects in place of strings.

  1. Convert the content type: If the app submits application/x-www-form-urlencoded, try converting the request to application/json or using bracket syntax like username[$ne]=dummy&password[$ne]=dummy.
  2. Observe the reaction: If supplying an object causes a server error, returns different records, or logs you in as the first user in the collection, the parameter is passed directly into a query filter without type checking.

Phase 2: Extracting Hidden Data (The Combination Lock) ​

What if the application only gives you a binary answer—such as "Login Successful" versus "Invalid Credentials"—and you need to find an unknown password or secret token?

You can treat the $regex operator like a digital combination lock. By anchoring your regular expression to the beginning of the string with ^, you can guess the secret character by character:

json
{"username": "admin", "password": {"$regex": "^a"}}
{"username": "admin", "password": {"$regex": "^b"}}
{"username": "admin", "password": {"$regex": "^c"}}
...
{"username": "admin", "password": {"$regex": "^s"}}  <-- Success! First letter is 's'
{"username": "admin", "password": {"$regex": "^sa"}}

Phase 3: Uncovering Unknown Fields with $where ​

In some databases, you might not even know what the secret field is named. Is it password? resetToken? api_key? secretToken?

In MongoDB, the $where operator allows developers to write arbitrary JavaScript code that executes directly on the database engine for each document evaluated:

javascript
// Server-side query using $where
db.users.find({ $where: "this.username == '" + req.body.username + "'" });

⚙️ Engine Variations: NoSQL Across the Industry

Not all NoSQL databases use MongoDB's syntax. Here is how injection manifests across other document and key-value stores:

  • MongoDB: BSON document operator injection ($ne, $regex), server-side JavaScript via $where, and aggregation pipeline injection ($lookup).
  • CouchDB: REST-based JSON queries. Unsanitized input can manipulate _all_docs, startkey, and endkey range filters.
  • Redis: Redis commands sent over raw sockets or through APIs. Passing unsanitized input can inject multi-line Redis commands or trigger EVAL Lua script execution.
  • Elasticsearch: Query DSL injection. Submitting unexpected JSON structures into _search can expose internal indices or trigger costly script queries.

Defensive Blueprint: How to Lock Down Document Databases ​

Preventing NoSQL injection requires building defenses that cannot be tricked by unexpected data types:

🛡️ The 4 Golden Rules of NoSQL Defense:

  1. Enforce strict type checking: Verify that incoming parameters are strictly primitive strings before using them in database queries (e.g., if (typeof req.body.password !== 'string') throw new Error('Invalid input');).
  2. Use schema validation: Employ schema libraries like Mongoose with strict type casting, or validation engines like Zod, Joi, or JSON Schema.
  3. Disable JavaScript execution: Turn off javascriptEnabled: false in MongoDB configuration to neutralize $where and mapReduce script execution.
  4. Never pass req.body directly: Explicitly pick only the exact fields you need rather than passing raw request objects into database find operations.
