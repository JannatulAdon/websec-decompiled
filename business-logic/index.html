Business Logic Vulnerabilities · When Valid Code Does Invalid Things ​

Business logic vulnerabilities are uniquely deceptive: every single component can be running bug-free, perfectly syntax-validated, and cryptographically sound, yet the entire system remains completely broken. Logic flaws happen when developers build software around unspoken assumptions about how humans behave in the real world.

💡 Everyday Analogy: The Vending Machine Return Slot. Imagine a vending machine where inserting $5 lets you purchase a $2 bottle of water, returning $3 in change. What happens if you press a button that requests negative one bottles of water? If the machine's computer calculates Total = -1 × $2 = -$2 and computes your change as Inserted ($5) - Total (-$2) = $7, the machine just handed you free money! The math is technically consistent, but the real-world business rule—"a customer cannot buy negative goods"—was never written into the software.

Case File #6: Tracing Price Manipulation Behind the Scenes ​

Let's examine what happens when an online shopper adds an expensive luxury item to their cart:

🔎 Step 1 · What You Notice in the Browser

You add a $1,337 leather jacket to your shopping cart. In your proxy history, you inspect the HTTP POST request sent when clicking "Add to Cart": productId=1&price=133700&quantity=1.

⚙️ Step 2 · What the Server Does Behind the Scenes

The backend shopping cart handler receives the request parameters and computes the line-item total by multiplying the incoming price by the incoming quantity before storing it in the user's active session cart:

Blue = Server Computation LogicGold = Parameter Trusted from Client
item_price = request.body.price; // Trusted straight from browser!
total_charge = item_price * request.body.quantity;
cart.append({ id: 1, total: total_charge });
💥 Step 3 · Where the Logic Breaks

The developers assumed the browser UI would always send the legitimate $1,337 price. By intercepting the request and changing price=133700 to price=1 (or sending a negative quantity to cancel out expensive items), the user pays a single penny for a luxury jacket. The checkout code validates that the user's payment covers the cart total, and the order ships!

🛡️ Step 4 · How Developers Lock It Down

Never accept prices, discount flags, or financial figures from client HTTP requests. Look up the authoritative price directly from the database server-side using the product ID. Validate that all quantities are strictly positive integers within reasonable application boundaries.

Visual Comparison: UI Expectations vs. Proxy Reality ​

💭 What the Developer Expected

The web page dropdown only provides quantity choices from 1 to 10, and prices are rendered cleanly from our database, so no user could ever submit an invalid price or negative quantity.

💥 What Actually Happened

The client controls the raw HTTP request completely. An attacker uses an intercepting proxy to modify prices, duplicate coupons, or skip prerequisite workflow steps entirely.

Client-Side Controls and Untrusted Inputs ​

Client-side controls (like disabled HTML buttons, JavaScript validation, or hidden form fields) are visual conveniences for legitimate users, not security barriers. When an application trusts numbers supplied by the client:

  • Price Tampering: Setting the price to a negligible amount ($0.01) or zero.
  • Negative Quantities: Ordering 1 expensive item ($1,000) and -99 cheap items ($10 each) to produce a net cart total of $10!
  • Integer Limits & Overflows: Submitting quantities so huge (e.g., above 2,147,483,647 in 32-bit signed integers) that the total wraps around to a negative number or zero.

🔬 Under the Hood: Why Integer Overflow Still Matters in Modern Apps

In languages and databases using fixed-width integers (such as 32-bit signed integers in C, Java, or SQL INT), numbers wrap around when they exceed the maximum value: 2,147,483,647 + 1 = -2,147,483,648

If an e-commerce checkout multiplies quantity × price without bounds checking, an attacker can choose a quantity where the product wraps into a negative total. Many shopping cart engines interpret negative totals as store credits or treat any payment of $0 as paid in full.

Coupons, Refunds, and Rule Interactions ​

Logic flaws frequently hide in the seams between different business rules that make sense in isolation but break when combined:

  • Coupon Stacking Loops: A store offers two discount codes: NEWCUSTOMER (20% off) and SPRING10 ($10 off). The UI prevents entering both. However, submitting alternating requests applies both codes repeatedly until the cart total drops to zero.
  • Gift Card Balance Transfer: A gift card redemption endpoint deposits money into the user account without locking the card or checking if the card was already redeemed in the same session.
  • Asymmetric Refunds: The system calculates a 30% discount on purchase, but the refund module refunds the original full catalog price upon return!

Workflow Validation and Flawed State Machines ​

Applications frequently model complex workflows (checkout wizards, MFA logins, account registrations) as multi-step state machines. A state machine flaw📖 Workflow / Step-Skipping FlawWhen a website assumes you will always click Step 1 → Step 2 → Step 3 in order, and forgets to check if you jumped straight from Step 1 to Step 3.💡 Real-life analogy: Walking past the cash register straight to the "Pickup Counter" because the pickup clerk assumes anyone standing there already paid. occurs when the server assumes users will always proceed strictly through Step 1 → Step 2 → Step 3:

  • Skipping Mandatory Steps: Navigating directly to Step 3 (/checkout/complete) without executing Step 2 (/checkout/payment).
  • Dual-Use Endpoints: An endpoint designed for account registration is re-used for password updates without re-verifying the caller's existing password.
  • Canceling Out of Mid-Flight States: Aborting a 2FA prompt midway through login while retaining the initial authenticated session.

Input Parsing Discrepancies and Boundary Cases ​

When two different components in an architecture parse the exact same input using different rules, logic breaks down:

  • Email Normalization & Truncation: A registration form accepts a 255-character email, but the database column only stores 100 characters. Submitting admin@target.com.attacker.com truncated at character 16 creates an account officially registered as admin@target.com!
  • Domain Parsing Differences: An access-control filter checks if an email ends with @target.com, while the internal notification worker parses comments or subdomains differently.

Cryptographic Oracles in Business Flows ​

When an application exposes endpoints that encrypt user data and later decrypt it (for example, generating encrypted cookies for "track my order" features), an investigator can use the application as an encryption oracle. By feeding crafted plaintext into the encryption helper and capturing the resulting ciphertext, they can forge administrative session tokens without ever knowing the server's private secret key.

⚙️ Engine Variations: How Frameworks Parse Duplicate Parameters

When an HTTP request contains duplicate parameter names (price=100&price=0.01):

  • PHP: Keeps the last value (price=0.01).
  • ASP.NET: Concatenates all values with commas (price=100,0.01).
  • Express / Node (qs): Converts duplicate parameters into an array (price = ['100', '0.01']).
  • Java Servlets: Returns an array via getParameterValues() or the first value via getParameter().

If a security firewall checks the first parameter while the application processes the last, parameter pollution completely dismantles business validation.

🛡️ Core Defensive Checklist: Re-derive all authoritative values server-side. Never trust prices, quantities, or privilege levels from the client. Enforce explicit state machine transition checks (ensure Step N cannot occur unless Step N-1 succeeded). Enforce database constraints (such as non-negative balance checks and unique coupon records), and audit business logic flows against concurrent and out-of-order execution.
