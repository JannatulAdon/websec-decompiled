API Testing · The Core Investigation ​

Modern web applications are divided into two distinct halves: a sleek frontend user interface and a busy backstage API. Vulnerabilities emerge because backend APIs often trust incoming requests far more than the frontend does—accepting administrative fields, unadvertised HTTP methods, and parameter tricks that no browser button ever triggers.

💡 Everyday Analogy: The Restaurant Kitchen Hatch. The dining room menu only lists soup and salad, and the waiter won't let you order a prime ribeye. But if you walk straight up to the kitchen service hatch and hand the cook an order ticket marked "1x Prime Ribeye, Price: $0.00", a busy kitchen following automated recipes might prepare and serve it without question. An API is that kitchen hatch: if it doesn't verify authorization independently of the dining room menu, visitors can order whatever the backend knows how to cook.

Case File #1: The Unchecked Profile Update ​

Let's trace what happens when you update your email address in an account settings portal.

🔎 Step 1 · What You Notice in the Browser

You type a new email into the profile form and click "Save". Your browser sends an HTTP PATCH /api/users/1337 request carrying a simple JSON body: {"email": "detective@example.com"}.

⚙️ Step 2 · What the Server Does Behind the Scenes

The backend API framework parses the incoming JSON string and automatically binds its keys directly into the server's internal User database entity using framework auto-binding (such as Spring's model mapper or Node's Object.assign).

Blue = Server Model FieldsGold = Client JSON Payload
User.update({"email": "detective@example.com"})
💥 Step 3 · Where the Logic Breaks

The frontend HTML form only offered an email input, but the backend User model also possesses attributes like role, isAdmin, and tier. Because the API binds whatever JSON keys are supplied without an allow-list, adding "role": "administrator" to the raw request quietly elevates the user's account privileges—a classic mass assignment📖 Mass Assignment (Auto-Binding)When an API automatically copies every field from a user’s JSON request directly into a database user record—including hidden fields like `"isAdmin": true`.💡 Real-life analogy: A self-checkout kiosk that lets customers scan their own "Employee 100% Discount" barcode if they bring one from home. flaw.

🛡️ Step 4 · How Developers Lock It Down

Developers define explicit Data Transfer Objects (DTOs) with strict allow-lists for each endpoint. Instead of binding raw input to the database model, the server only reads explicitly permitted fields and discards or rejects all extraneous properties.

The developer assumed that because the web page form only presents inputs for email and username, the API endpoint would only ever receive those two properties from clients.

The Detective's Investigation Playbook ​

1. Endpoint Discovery & Hidden Blueprints ​

APIs rarely hide their documentation completely. Developers often leave interactive documentation frameworks active in production or embed API endpoints inside compiled JavaScript bundles:

  • Standard Documentation Paths: Check for /api, /api/docs, /swagger, /swagger.json, /swagger-ui.html, /openapi.json, and /api/v1/.
  • HTTP Method Probing: If GET /api/products/1 returns a product, test sending OPTIONS /api/products/1 to see allowed verbs (GET, POST, PUT, DELETE), or try DELETE /api/products/1.
  • Client-Side Source Bundles: Search downloaded JavaScript files for API path patterns like "/api/", "baseURL", and parameter names.

2. Mass Assignment (Auto-Binding) ​

In modern web frameworks, model-binding utilities make life easy for developers by automatically mapping request parameters directly onto internal database models. When an application accepts a user submission without an explicit allow-list, any internal property of the object can be overwritten.

🔬 Under the Hood: Why Frameworks Auto-Bind by Default

Different application frameworks implement auto-binding through reflection:

  • Spring (Java): @ModelAttribute and Jackson object mapper inspect setter methods and invoke any setter that matches an incoming JSON field.
  • Ruby on Rails: Calling User.new(params[:user]) without using params.require(:user).permit(...) ("strong parameters") binds every submitted key.
  • Django REST Framework (Python): Serializers configured with fields = "__all__" expose all model fields for update unless explicitly set to read_only_fields.
  • Node.js / Express: Code using Object.assign(user, req.body) or user.set(req.body) copies every property into the user model.

The secure architectural pattern is Input Allow-Listing: use dedicated request DTOs that only contain fields meant to be modified by the current caller.

⚙️ Engine Variations: How Parsers Handle Duplicate Parameters

When a query string contains duplicate parameters (e.g., ?role=user&role=admin), different backend technologies choose different values:

Framework / EngineDuplicate Parameter BehaviorExample: ?user=alice&user=bob
PHP / ApacheUses the last occurrenceValue is "bob"
Node.js / Express (qs)Creates an arrayValue is ["alice", "bob"]
ASP.NETJoins with commaValue is "alice,bob"
Go (net/url)URL.Query().Get() takes the firstValue is "alice"
Python (Flask/urllib)request.args.get() takes the firstValue is "alice"

Parameter pollution exploits the disagreement between what a frontend security check validates (e.g., the first parameter) and what the backend execution engine consumes (e.g., the last parameter).

The Detective's API Testing Routine ​

When auditing an unfamiliar API surface:

  1. Map the Surface: Review API documentation files (/swagger, /openapi.json) and extract API route strings from client-side .js bundles.
  2. Probe HTTP Verbs: Try alternate HTTP verbs (PUT, DELETE, PATCH, OPTIONS) on read-only endpoints.
  3. Inspect Payloads for Auto-Binding: On POST and PATCH requests, inspect the response body. If the response displays fields not present in the request (e.g., role, status, balance), add those properties to your submission.
  4. Test Parameter Pollution: Insert URL-encoded delimiters (%26, %23, %3F, ../) into query parameters and REST path segments to determine if internal requests can be reshaped.
  5. Vary Content-Type: Change application/x-www-form-urlencoded to application/json or application/xml to test whether alternate backend parsers are exposed.

How Developers Lock It Down Permanently ​

🛡️ The Golden Rules of Secure API Design:

  • Use Strict Request DTOs: Never bind incoming request bodies directly into database models. Use explicit Data Transfer Objects that only declare fields the caller is authorized to modify.
  • Disable Unused HTTP Verbs: Explicitly configure routers to reject unneeded methods with 405 Method Not Allowed rather than leaving default CRUD handlers open.
  • Build Safe Internal URLs: Never concatenate user input into internal API URLs using strings. Use URL builder libraries that automatically encode parameters properly.
  • Protect API Documentation: Restrict interactive API consoles (Swagger UI, GraphiQL) in production to authenticated internal networks.
  • Validate Schema Rigorously: Reject any request carrying unknown properties with 400 Bad Request rather than silently dropping or passing them.
