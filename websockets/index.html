WebSockets · The Case of the Open Intercom ​

A WebSocket is a persistent, two-way communication channel between a browser and a server. While traditional HTTP requests are like sending individual letters back and forth, a WebSocket is an open telephone line. But here is the critical discovery: once a WebSocket is established, it completely bypasses the browser's Same-Origin Policy—making handshake authorization and message validation essential.

💡 Everyday Analogy: The Open Intercom Line. Imagine an office intercom connecting your private desk directly to a storage room. Traditional HTTP is like sending written memos through mail inspection. A WebSocket, however, is a live intercom wire: once someone presses the buzzer and opens the line, both ends can speak instantly without further inspection. If you don't check who pressed the buzzer during the initial connection, an eavesdropper can dial in, listen to private conversations, and shout orders into the room.

Case File #1: Cross-Site WebSocket Hijacking (CSWSH) ​

Let's trace how an external site can tap into your live chat session.

🔎 Step 1 · What You Notice in the Browser

You are logged into a customer service portal on support.example and chatting with a representative. Messages appear instantly in the chat window without page refreshes.

⚙️ Step 2 · What the Server Does Behind the Scenes

While that chat is open, you visit an attacker's website on evil.example. JavaScript on their page runs new WebSocket('wss://support.example/chat'). The browser initiates an HTTP Upgrade request, automatically attaching your valid session cookie:

Blue = Browser Handshake Headers & Valid SessionGold = Attacker's Origin Header
GET /chat HTTP/1.1
Host: support.example
Upgrade: websocket
Connection: Upgrade
Cookie: session=9c4a8f10e7b23d
Origin: https://evil.example
💥 Step 3 · Where the Logic Breaks

The server sees a valid session cookie and answers 101 Switching Protocols. Because the Same-Origin Policy does not restrict WebSocket connections, the server ignores the Origin header! The attacker's script now receives all real-time chat messages and can send messages in the victim's name.

🛡️ Step 4 · How Developers Lock It Down

Developers strictly validate the Origin header against an approved domain allow-list during the handshake. Additionally, servers require a one-time, unpredictable connection token (like an anti-CSRF token) in the upgrade request to confirm intentional user authorization.

Visual Comparison: HTTP Same-Origin Policy vs. Unrestricted WebSockets ​

💭 What the Developer Expected

The developer assumed that because standard HTTP requests require CORS headers to read data across origins, WebSockets would naturally provide the same cross-origin protections.

💥 What Actually Happened

WebSockets are not constrained by CORS. Any website on the internet can establish a WebSocket connection to the server, and the browser will attach the user's session cookies automatically.

The WebSocket Connection Lifecycle ​

From initial HTTP upgrade to continuous data frames, a WebSocket connection moves through five distinct checkpoints:

1. Upgrade Handshake Client sends HTTP request with Upgrade: websocket and session cookie.
→
2. Origin & Auth Check Server validates Origin header and verifies session credentials.
→
3. 101 Switching Protocols Connection transitions from HTTP to a persistent TCP socket.
→
4. Bi-Directional Frames Client and server exchange text or binary messages continuously.
→
5. Message Validation Every incoming frame must be parsed, validated, and encoded.
🔬 Under the Hood: Why WebSockets are Not Covered by CORS

CORS exists to restrict fetch() and XMLHttpRequest responses inside the browser. When a browser initiates a WebSocket connection, it sends a standard HTTP handshake. However:

  1. The browser does not require the server to return Access-Control-Allow-Origin before establishing the socket.
  2. Any Access-Control-Allow-Origin headers returned by the server are completely ignored by the WebSocket API.

The only line of defense against cross-site connection hijacking is the server manually inspecting the Origin header during the handshake and dropping unauthorized connections.

Message-Level Trust: Validating Every Frame ​

Opening a secure socket is only half the battle. Once connected, every message sent across the socket must be treated as untrusted user input:

  • Cross-Site Scripting (XSS): If a chat application broadcasts incoming WebSocket messages to other users without HTML entity encoding, an investigator can send an XSS payload through a socket frame to trigger stored XSS on all connected clients.
  • Server-Side Injection: Just like HTTP parameters, messages sent over WebSockets can flow into database queries (SQLi) or system commands if not properly parameterized.

Handshake Header Manipulation ​

The initial HTTP Upgrade handshake is subject to the same tampering as any regular web request:

  • IP-Based Restrictions: If a server uses IP allow-lists or rate limits to protect its socket endpoint, spoofing headers like X-Forwarded-For may bypass those controls if reverse proxies are misconfigured.
  • Session Replay: If the WebSocket handshake does not bind the socket to the authenticated session state, replaying handshake parameters may grant unauthorized access.

⚙️ Architecture & Server Quirks: How WebSockets Differ by Stack
  • Nginx Reverse Proxying: Requires explicit configuration directives (proxy_set_header Upgrade $http_upgrade and proxy_set_header Connection "upgrade"). A misconfigured proxy may strip upgrade headers or mishandle connections.
  • Node.js ws library: By default, ws does not verify the Origin header. Developers must explicitly implement the verifyClient callback.
  • Socket.IO: Uses its own proprietary protocol on top of WebSockets and long-polling. It includes its own cors: { origin: ... } options which behave differently from raw WebSocket implementations.
  • HTTP/2 & HTTP/3: Traditional Upgrade: headers are forbidden in HTTP/2. Instead, RFC 8441 defines an extended CONNECT method for tunneling WebSockets over existing HTTP/2 streams.

🛡️ The Detective's Defense Blueprint. Always validate the Origin header against an explicit HTTPS allow-list during the handshake. Protect against CSWSH by generating a short-lived, single-use anti-CSRF ticket before opening the socket. Apply the same rigorous input validation and output encoding to WebSocket message frames as you would to standard REST API payloads.
