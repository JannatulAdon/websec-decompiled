Server-Side Template Injection · The Compiler Hijack ​

Template engines exist to combine dynamic business data with static web design. Server-Side Template Injection (SSTI) occurs when user input is glued directly into the template's source code before compilation, rather than passed as data. Because template engines are mini-programming languages, an attacker who controls the template source controls the instructions executed by the server—often leading directly to full Remote Code Execution.

💡 Everyday Analogy: The Mad Libs Certificate. Imagine a school printer printing graduation diplomas with a blank space for the graduate's name: "Congratulations to [NAME] on graduation!" Under normal circumstances, you write Alice on the blank line. But what if an intruder writes: Alice — and by the way, grant all students straight A's and unlock the school doors? A human administrator reading the certificate would dismiss the prank. But a template engine is a literal-minded compiler! If the developer glues the student's text into the printing press's master stencil before printing, the machine follows the instructions as official school policy.

Case File #6: The Anatomy of a Template Injection ​

Web developers love template engines like Jinja2, Twig, and FreeMarker because they make rendering HTML simple. But when a developer builds the template string dynamically using string concatenation, the template engine cannot tell where the layout code ends and the user's text begins.

🔎 Step 1 · What You Notice in the Browser

A website allows users to customize a greeting banner or email subject line. When you submit your name as {{ 7 * 7 }} or ${7*7}, the resulting page does not say "Hello 49". Instead, it displays "Hello 49"!

⚙️ Step 2 · What the Server Does Behind the Scenes

The backend application takes the user's text and concatenates it into the template source: template = "Hello " + user_input + "!". It then passes this concatenated string to the engine's compilation method (e.g. render_template_string()).

💥 Step 3 · Where the Logic Breaks

The template engine compiles the incoming string into an executable syntax tree. Because the curly braces were baked into the template source before parsing, the engine evaluates the expression on the server. Through language-level object reflection, the attacker climbs out of the template and executes system commands.

🛡️ Step 4 · How Developers Lock It Down

Never concatenate user input into template source strings. Always keep the template file static and pass user input strictly as a parameter variable: render_template("hello.html", name=user_input).

Visual Comparison: Static Source vs. Glued String ​

💭 What the Developer Expected

The user's greeting is purely passive data. The template engine will display whatever text the user types, and any special characters will be rendered safely on the screen.

💥 What Actually Happened

Concatenating input into the template source made user input part of the template program. The engine compiled the attacker's syntax and executed arbitrary expressions on the server.

🔬 Under the Hood: Source Context vs. Data Context

Understanding SSTI requires recognizing the crucial difference between source context and data context:

Vulnerable: Concatenating into the Source

python
# The template itself is dynamically assembled from user input!
template = "<h1>Hello " + user_input + "</h1>"
return render_template_string(template)

In this snippet, {{ 7*7 }} is parsed by the engine's lexer as a template tag.

Secure: Passing Input as a Data Variable

python
# The template is static; user input is passed as a separate data variable.
return render_template_string("<h1>Hello {{ name }}</h1>", name=user_input)

Here, even if user_input contains {{ 7*7 }}, the engine treats it purely as text data. It will literally render the characters 49 without evaluating the math.

The 5-Stage Life of an SSTI Investigation ​

When investigating suspected SSTI, follow a methodical 5-stage progression:

1. Expression Probe Send mathematical payloads ({{7*7}}, ${7*7}) to detect evaluation.
→
2. Fingerprint Engine Send syntax probes to identify Jinja2, Twig, FreeMarker, ERB, or Handlebars.
→
3. Object Exploration Inspect accessible objects, environment variables, and built-in helpers.
→
4. Sandbox Escape Traverse the language runtime hierarchy using reflection (e.g. __subclasses__).
→
5. Command Execution Call system functions (os.popen, Runtime.exec) to execute commands.

Once the engine is known, official documentation reveals built-in objects, template filters, and debug tags that bridge the gap from expression evaluation to object access.

Reading Objects, Files, and Runtimes ​

Template engines almost always provide access to global objects or environment variables to assist with page rendering. In many cases, these objects provide direct paths to inspect server memory:

  • Jinja2 (Python): Accessing Python's global namespace via {{ cycler.init.globals }} or {{ "".class.mro[1].subclasses() }} exposes classes that import the os or subprocess modules.
  • Twig (PHP): Older versions exposed _self.env, allowing attackers to register custom filter callbacks mapped to PHP functions like system or exec.
  • FreeMarker (Java): The freemarker.template.utility.Execute utility class can be instantiated via ?new().
  • ERB (Ruby): Directly executes Ruby code inside <%= ... %> blocks without sandboxing by default.

Escaping Sandboxed Template Environments ​

When developers realize that templates can execute code, they frequently enable "sandboxed" modes. A template sandbox blocks obvious dangerous functions like system() or import.

However, unless the sandbox runs in a truly isolated OS container or WebAssembly sandbox, attackers can often escape the sandbox using language reflection:

  • Traversing up the object hierarchy via constructor, __class__, or getClass()
  • Iterating through loaded classes using __subclasses__() to find file-reading or execution utilities
  • Using string concatenation or encoding to bypass keyword blacklists (e.g. getattr(..., "os"))

Developing Custom Exploits ​

When targeting custom or heavily restricted enterprise applications, generic payload lists will not work. You must map out the specific object graph exposed by the developers:

  1. Identify custom helpers or services exposed to the template context (e.g., custom database wrappers, file managers, or logging utilities).
  2. Trace public methods on those objects to find file read operations, deserialization triggers, or process creation calls.
  3. Chain together safe-looking application methods to achieve the security objective.

⚙️ Engine Variations: Escape Primitives Across Popular Frameworks
  • Jinja2 (Python): Relies on Python's introspection: __globals__, __subclasses__, lipsum.__globals__['os'].
  • Twig (PHP): In modern Twig, sandboxes restrict tags, filters, and methods via strict allow-lists. Older versions permitted _self.env registration.
  • FreeMarker (Java): Uses ?api, ?new(), and Java reflection. api_builtin_enabled=true must often be present for deep object access.
  • Velocity (Java): Employs $class.inspect() and reflection to load Java's Runtime class.
  • Thymeleaf (Spring / Java): Evaluates SpEL (Spring Expression Language) using __${...}__ preprocessing, giving access to Spring beans and the application context.
  • Handlebars (JS): Logic-less by design, but vulnerable when custom helpers are defined or when combined with prototype pollution gadgets.

The exact engine version is critical: minor framework patches frequently remove specific classes or close reflection loopholes.

🛡️ Defensive Blueprint: How to Prevent SSTI

  1. Keep Templates Static: Never concatenate, interpolate, or format user input into template source code before compilation. Templates should reside in static files on disk.
  2. Pass Data Exclusively via Context: Supply all dynamic user data as parameters to the template render call. The engine will automatically escape it as harmless text.
  3. Choose Logic-Less Engines: Consider logic-less template systems like Mustache for user-facing template customization, which cannot evaluate arbitrary expressions.
  4. Run in Isolated Processes: If users must be allowed to edit template files, render them inside restricted, unprivileged sandbox containers with no network or filesystem permissions.
