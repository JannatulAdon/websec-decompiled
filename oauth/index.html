OAuth Authentication · The Untrusted Handshake ​

OAuth 2.0 was designed for delegated authorization—granting a service permission to read your calendar or photos without sharing your password. When modern websites bolt login authentication on top of OAuth, they create an intricate relay race between the browser, the application, and the identity provider where a single lax redirect rule can hand over the entire account.

💡 Everyday Analogy: The Valet Parking Claim Ticket. Imagine pulling up to a luxury hotel and handing your car keys to the valet. The valet gives you a numbered claim ticket that lets anyone holding it retrieve your car. Now imagine you drop the claim ticket on the sidewalk, or the valet hands your car keys to anyone wearing a jacket similar to yours without checking their room number or identity. That is what happens when OAuth leaks authorization codes: anyone who intercepts that claim ticket can redeem it for full access to the victim's account.

Case File #7: Following the OAuth Handshake Behind the Scenes ​

Let's trace what happens when you click "Log in with Social Account" on an e-commerce website:

🔎 Step 1 · What You Notice in the Browser

You click "Sign in with Social ID". Your browser redirects to the third-party provider's consent page: oauth.provider.com/auth?client_id=store_123&redirect_uri=https://store.com/oauth-callback&response_type=code&scope=email. You click "Authorize", and the provider redirects you back to the store with a code: https://store.com/oauth-callback?code=SECRET_AUTH_CODE.

⚙️ Step 2 · What the Server Does Behind the Scenes

The store's backend server grabs the code from the redirect URL, connects directly to the identity provider's backstage API endpoint, exchanges the code for an access token, and fetches your email address to log you in:

Blue = Legitimate Registered CallbackGold = Tampered Parameter / Leakage Target
redirect_uri=https://store.com/oauth-callback/../../attacker.com/capture
💥 Step 3 · Where the Logic Breaks

The authorization server used loose pattern matching or path traversal on the redirect_uri📖 OAuth & redirect_uriWhen you click "Sign in with Google/GitHub," `redirect_uri` is the return address where the login service sends your secret access ticket.💡 Real-life analogy: Telling the post office where to forward your passport—if an attacker can change that forwarding address, your passport goes to their mailbox. parameter instead of enforcing an exact string match. As a result, the victim's secret authorization code is redirected straight into an external server log controlled by the attacker, allowing them to redeem the victim's login session!

🛡️ Step 4 · How Developers Lock It Down

Enforce strict, exact string matching for all registered redirect_uri endpoints on the authorization server. Always include an unpredictable, cryptographically random state parameter bound to the user's browser session to prevent login CSRF, and adopt Authorization Code with PKCE (Proof Key for Code Exchange).

2. Consent & Grant User logs in at provider and consents to share profile.

Implicit Flow and Redirect URI Leakage ​

In legacy OAuth implementations, applications often relied on the Implicit Grant Flow, where the authorization server delivers access tokens directly in the URL fragment (#access_token=...) to the browser instead of returning an authorization code to the backend.

Because tokens exist directly in the browser's address bar:

  • Any open redirect or third-party script on the callback page can steal the token.
  • Web proxies, browser extensions, or Referer headers can leak the fragment to untrusted destinations.
  • If the application trusts profile emails sent directly from the client without verifying the server-side signature, an attacker can substitute any victim's email address and take over their account.

🔬 Under the Hood: Why URL Matching in OAuth Is Deceptively Difficult

When validating incoming redirect_uri parameters, authorization servers frequently make subtle parsing errors:

  • Prefix Matching Flaws: Checking uri.startsWith("https://example.com/callback") erroneously approves https://example.com/callback.attacker.com.
  • Domain Wildcards: Allowing https://*.example.com/callback enables any compromised subdomain, XSS flaw, or open redirect on any subdomain to capture codes.
  • Path Traversal in Redirects: Sending https://example.com/oauth/callback/../../open-redirect resolves after validation, redirecting codes through an internal open redirect.

Profile Linking and Missing state Parameters ​

Many websites let users link their existing account to an external Google or GitHub identity for fast logins. The state parameter is designed as a CSRF token to prove that the person completing the OAuth flow is the same person who started it.

If an application omits or fails to validate the state parameter:

  1. An attacker starts the OAuth link flow with their own social media account and captures the authorization code before it is redeemed.
  2. The attacker tricks a logged-in victim into clicking that callback URL.
  3. The victim's application account becomes permanently bound to the attacker's social login identity, allowing the attacker to sign into the victim's account anytime!

Token Theft via Open Redirects and Proxy Pages ​

Even if the authorization server enforces strict redirect_uri validation, attackers look for secondary hops on the client website:

  • Chaining with Open Redirects: If the registered callback page contains an open redirect parameter (e.g. https://client.com/callback?next=https://attacker.com), the OAuth code or fragment lands on the client site and is instantly forwarded to the attacker.
  • Proxy Pages & PostMessage Leaks: If a website loads an external widget inside an iframe or uses window.postMessage without origin restrictions, the access token stored in the parent window can be harvested across origins.

Dynamic Client Registration and SSRF ​

The OpenID Connect standard includes an optional Dynamic Client Registration specification that allows third-party client apps to register themselves automatically by submitting JSON metadata to /register.

If this endpoint is left publicly accessible without proper authentication and URL sanitization:

  • An attacker can register a malicious client application with custom redirect endpoints.
  • If the server accepts URLs for client logos (logo_uri) or cryptographic keys (jwks_uri), the server may fetch these URLs internally—introducing a high-impact Server-Side Request Forgery (SSRF📖 SSRF & Internal Loopback (127.0.0.1)Tricking a public web server into fetching a URL that points to its own private internal network (`localhost` or `169.254.169.254`) that outsiders cannot reach directly.💡 Real-life analogy: Calling a receptionist inside a high-security building and asking them to read aloud a document pinned to the breakroom wall behind them.) vulnerability into internal infrastructure.

⚙️ Engine Variations: How Major Identity Providers Handle Callbacks
  • Google OAuth: Enforces byte-for-byte exact matching on redirect_uri. Wildcards are strictly disallowed (with an exception for http://localhost on loopback development).
  • GitHub OAuth: Matches based on subpath hierarchies; query parameters are ignored during comparison, which can interact unexpectedly with client routers.
  • Microsoft Azure AD / Entra: Supports wildcard redirects for Single Page Applications (SPAs), making misconfiguration and tenant-wide token leakage a recurring risk.
  • Keycloak: Supports regex patterns in Valid Redirect URIs; entering https://app.com/* allows path traversal attacks.

🛡️ Core Defensive Checklist: Always enforce exact, literal string matching for all redirect URIs on authorization servers. Always generate and validate a cryptographically secure, session-bound state parameter on every OAuth transaction to prevent login CSRF. Prefer the Authorization Code flow with PKCE over legacy Implicit flow, and never link third-party accounts without re-authenticating the current session.
